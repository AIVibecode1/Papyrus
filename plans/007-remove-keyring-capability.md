## Why this matters

The webview capability set grants `keyring:default` — which enables the
plugin's full IPC surface (`allow-get-password`, `allow-set-password`,
`allow-delete-password`, plus the secret variants) with **no service or
account scoping** (per the vendored plugin's `permissions/autogenerated/
reference.md`). The frontend never calls the keyring JS API — every key
operation is Rust-side (`ai.rs` `load_key`/`save_api_key`/`delete_api_key`/
`has_api_key` via `KeyringExt`). The permission is therefore dead surface
that turns any future webview script execution (XSS) into total credential
exfiltration with zero additional steps. Removing it costs nothing and
honors the project's own least-privilege rule (AGENTS.md). Also trims
`opener:default` to only what the app uses.

## Steps

### Step 1: Drop keyring:default, trim opener

In `src-tauri/capabilities/default.json`, replace the permissions array with:

```json
  "permissions": [
    "core:default",
    "opener:allow-open-url"
  ]
```

Notes:

- `opener:allow-open-url` is the only opener permission the app needs
  (PDF links via `openUrl`); the app never calls `revealItemInDir` or
  `openPath`.
- Verify the permission identifier exists: check
  `src-tauri/gen/schemas/desktop-schema.json` (regenerated by the build) for
  `opener:allow-open-url`; the Tauri CLI validates unknown permissions at
  build time and will error if the name is wrong — if it errors, the correct
  identifier can be found in the plugin's generated reference under
  `src-tauri/gen/schemas/` after a build, or from the upstream repo
  `tauri-apps/plugins-workspace/plugins/opener/permissions/autogenerated/`.

**Verify**: `cd src-tauri && cargo check` → Finished, no warnings.
Then `cd src-tauri && cargo build` → exit 0 (validates the capability
schema against the generated schemas).

### Step 2: Smoke-test that keys still work end to end

- `cargo build` above produces the dev binary; run the existing test suite
  (`cargo test --lib`) — the keyring commands are not unit-tested (they
  need the OS keychain), so verification here is: the app still compiles
  with the trimmed capabilities, and the frontend typecheck passes
  (`pnpm exec tsc --noEmit`).
- Manual verification (operator): run `pnpm exec tauri dev`, add a provider
  with a key in Settings, confirm "Key saved" badge appears, Test works,
  delete works. This is the operator's call — the plan's machine checks are
  the compile gates above.

**Verify**: `pnpm exec tsc --noEmit` → exit 0; `cargo test --lib` → all pass.

## Maintenance notes

- If a future feature needs the webview to access the keychain directly,
  add the narrowest permission with explicit scoping if the plugin supports
  it — never `keyring:default` wholesale.
- This plan is a prerequisite for plan 023 (CSP hardening): with the
  keyring IPC surface removed, the remaining webview attack value is
  lower, which makes a `script-src 'self'` CSP a stronger guarantee.
